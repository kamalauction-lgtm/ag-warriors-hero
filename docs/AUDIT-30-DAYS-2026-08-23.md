### 3. Curriculum versioning — submissions are not version-safe 🔴

`task_submissions` stores `day_id` (a pointer to a **mutable row**) and `day_no`. It does **not** store `curriculum_version_id`, a content hash, or an `xp_amount` snapshot.

`Admin.tsx:97` does `supabase.from('curriculum_days').update(patch)` **in place**; its own toast says *"live for all cohorts on v1"*. And `fn_review_submission` re-reads `curriculum_days.xp_amount` **at review time**.

Consequence: editing a day silently rewrites what every past submission was answered against, and editing XP retroactively changes the value of approvals that have not yet been reviewed. **There is also no audit event on curriculum edits.**

### 4. RLS insert holes — the two most serious defects 🔴🔴

```sql
create policy w_subs_self on task_submissions
  for all using (<ownership predicate>)
  with check (status in ('in_progress','submitted'));     -- 002_challenge.sql:238-240
```

For **INSERT**, Postgres applies `WITH CHECK` **instead of** `USING`. The ownership predicate is only in `USING`. Therefore **any authenticated user can insert a task submission for any `enrolment_id`, any `day_no`, at any stage** — bypassing `fn_submit_task` entirely (which is the only place the "day is locked" and "enrolment is active and yours" checks live).

The identical hole exists on `readiness_submissions` (`w_ready_self`).

Because the policy is `FOR ALL`, participants also hold **DELETE** on their own submission history — the "resubmissions keep history" guarantee is convention, not enforcement.

### 7. Country resolution — `country_override` is dead **and hazardous** 🟠

```sql
country_override country_t,                 -- null = both countries
unique (version_id, day_no, country_override)
```
Postgres treats NULLs as distinct in a UNIQUE index, so the constraint permits **unlimited duplicate generic rows** — the exact row that needs protecting.

Both read paths carry **no country filter and no deterministic tie-break**:
- server `fn_submit_task:88` → `… where version_id=? and day_no=? limit 1` (no `ORDER BY`)
- client `Challenge.tsx:59` → `.eq('version_id', …).order('day_no')` then `Array.find`
- admin editor `Admin.tsx:81` → `.select('*').order('day_no')`, **no filter at all**

So if a MY row and a generic row both existed for Day 8, an **ID warrior could be served the MY variant**, and `day_id` on the submission could point at a different row than the one they read. A repo-wide grep for `country_override` returns **two hits, both the DDL**.

Country separation is actually achieved a different way — **two cohorts sharing one curriculum version, localised by trilingual jsonb**. That is the working design. `country_override` is an unfinished second mechanism for the same goal.

### 8. Cohort clock — correct today, correct by accident 🟠

```sql
greatest(0, least(30, (current_date at time zone c.official_timezone)::date - c.official_start_date + 1))
```
Postgres resolves this as `timestamptz AT TIME ZONE zone → timestamp`: UTC midnight → KL 08:00 → date unchanged. So for **any positive UTC offset (MY +08, ID +07) it is a no-op** and the result is simply the UTC date. Measured = **16** ✅.

But:
- The day rolls over at **00:00 UTC = 08:00 MYT / 07:00 WIB**, not local midnight.
- **`daily_unlock_time` (06:00) is read by nothing** — dead column.
- `greatest(0, least(30, …))` clamps at 30 forever; there is no "cohort finished" signal distinct from "day 30".
- No grace window; past days never close.

### 10. Streaks — a curriculum metric, not a discipline metric 🟠

`challenge_streak()` counts the run of consecutive **`day_no` integers** ending at the highest approved day. It never touches a date, a clock, `cohort_day()`, `submitted_at` or `reviewed_at`.

- Not persisted; recomputed on every call.
